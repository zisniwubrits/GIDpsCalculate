## 0. 动手前先概述（重要，用户要求）

**每次动手之前，先用一两句话向用户概述"我接下来要做什么"**（改哪个文件、加什么函数、跑什么命令），
然后再执行。不要把多步操作一次性闷头做完才汇报。

- 一步一个原子逻辑；每步做完报结果（改了什么、测试多少 passed、提交号）；
- 概述里要写清"是否会碰 `graph.py` / 前端 / HTTP"，让用户一眼判断影响面；
- 发现方向不对就停下来说，不要"先做了再说"。

## 0.1 定位（重要）

- **纯后端、纯 Python 层**：只写到 `genshin_dmg/relic.py` 里的函数，**不出 HTTP 接口、不改 `/api/schema`、不动前端**。
- **包里自带副本，不 import 主程序**（用户口径，2025 变更）：参考表 → `relic_tables.py`，
  通用公式/工具（`mangle` / 全角表 / 抗性系数 / 防御系数）→ `relic_math.py`。
  副本与主体的一致性由 `tests/test_relic_independence.py` 对拍守住；整目录搬走时连同该测试一起删。
- 现阶段**不碰 `graph.py`**。将来若要接伤害链（`Graph.extra_own` 之类），必须单独提交，并带上全部既有后端测试的回归。

## 0.2 「怪我没讲清楚，也怪你没问清楚」

这句话是用户原话，作为协作准则保留：

- **用户讲得不清楚，是双方的失误**：AI 不能在动手后才说"你没说清"，也不能拿它当返工的理由；
  用户也承认口径没一次讲全。责任对半，流程上以**先问清再动手**为准。
- AI 的具体义务：
  1. 把用户的话**复述成可检验的规格**（输入 / 输出 / 边界 / 判据），先让用户确认再写码；
  2. 发现"用户的前提与代码事实不符"时，**先摆证据**（跑一遍、给出实测数字），再问要不要改——
     不要照着错误理解直接改（例：`(3,0,0,2,0)` 是**投影**状态，不是"这件只有 2 条词条"）；
  3. 一个回合内把**能问的歧义一次问完**，用带选项的提问（含推荐项），不要挤牙膏式反复追问；
  4. 宁可多花一轮确认，也不要按错误理解写一整块代码后再回滚。
- 结论要落到文档/提交信息里，写清"为什么这么定"，方便以后回溯。

## 1. 口径（已与用户确认，改动前必须问）

### 1.0 三级近似（用户指定，改之前必须问）

整套计算只做**一阶、二阶、三阶**三个近似，其余一律精确枚举：

| 阶 | 近似 | 代码常量 | 含义 |
|---|---|---|---|
| **一阶** | 5 个部位**严格等概率** | `SLOT_SHARE = 1/5` | 想指定部位就必须乘 1/5（否则成本偏小 5 倍，踩过） |
| **二阶** | 副本两个套装**严格等概率** | `SET_SHARE = 0.5` | 目标套件数 = 掉落件数 × 1/2；散件槽不乘 |
| **三阶** | 初始词条数**严格 3:4 = 4:1** | `FOUR_SUB_RATE = 0.2` | 80% 三词条起手、20% 四词条起手（BOSS/周本/三合一的 34% 只作可选参数） |

三条都是"**严格**等概率/严格比例"，不要引入武器/部位偏好、幸运值、保底之类的东西。

### 刷取

| 项 | 口径 |
|---|---|
| 副本消耗 | **20 原粹树脂 / 次** |
| 每次产出 | 必掉 1 件五星 + **6.5%** 再掉 1 件 → **1.065 件/次** |
| 部位 | 5 个部位各 **1/5**（一阶近似）；要"指定部位"就乘 1/5 |
| 套装 | 副本两套各 **50%**；做 4 件套要目标套，另**允许 1 个散件槽**（任意套） |
| 树脂上限 | 200（只影响"天数"换算，当前不按天数算） |
| 浓缩树脂 | 暂不建模 |

### 主词条（随机掉落，不能自选）

- 花：固定生命 4780；羽：固定攻击 311
- 沙（5）：生命% / 攻击% / 防御% / 充能 / 精通
- 杯（**12**）：8 类属性伤害（7 元素 + **物理**，各 **5%**）+ 攻击% / 生命% / 防御% / 精通
- 冠（7）：生命% / 攻击% / 防御% / 精通 / 暴击率 / 暴击伤害 / 治疗
- 三张概率表各自合计 **100%**（由 `tests/test_relic.py` 守住）

### 副词条

| 词条 | 权重 |
|---|---|
| 固定生命 / 固定攻击 / 固定防御 | 150 |
| 暴击率 / 暴击伤害 | 75 |
| 生命% / 攻击% / 防御% / 充能 / 精通 | 100 |
| **合计** | **1100** |

- 抽取：**按权重、不放回**（4 条各不相同，且不与主词条同名）；元素伤害/物理/治疗没有对应副词条 → 池是满的 10 项。
- 初始条数：**副本 20% 是 4 条**（BOSS/周本/深渊盒/三合一 34%）。
- 强化：+4/+8/+12/+16/+20 共 **5 次**，每次在**已有副词条**里等概率挑一条；
  3 条起手时 **+4 级先补第 4 条**。
- 每件点数：4 条起手 **9 点**、3 条起手 **8 点** → 副本期望 **8.2 点/件**。

### 数值

- **词条值一律取平均值**（用户当前口径简化）：初始与强化都按 `relic_tables.RELIC_ROWS` 第 4 列，
  于是"一件圣遗物 = 每个属性的**词条次数**整数向量"。
- 满级主词条值见 `MAIN_STAT_VALUE`（五星 +20）。
- 4 件套的**效果数值不建模**（用户在圣遗物域里自己固定）。

### 筛选（有效词条 + 接受条件，用户口径，见 §12）

| 项 | 口径 |
|---|---|
| 「明显有效词条」 | **用户给定的一组属性**，可从副词条池 10 项里任选 **1~10 项**（攻击型常见 4~5，辅助可能 1 项） |
| 判定时机 | 4 条起手在 **+0**（4 条全可见）；3 条起手在 **+4**（补出第 4 条之后） |
| 接受条件 | 这 4 条里属于有效词条的**条数 ≥ k**（k 由用户给） |
| 未通过 | **直接丢弃**：不投强化、不产出（条件分布，不是混合分布） |
| 通过 | 继续强化到 +20：4 起手再 5 次（9 点）、3 起手再 4 次（8 点） |
| 成本 | **只算树脂**；垃圾胚子本身就是强化材料，不额外算摩拉/经验 |

## 2. 代码约定

- **键一律 ASCII**：槽位 `flower / plume / sands / goblet / circlet`；
  副词条键与面板宏同名（`crit_rate / crit_dmg / atk_pct / atk_flat / hp_pct / em / er / …`）。
  中文只放显示标签（`SLOT_LABELS` / `SUBSTAT_LABELS`），**不得当字典键**。
- **数值单一来源 = 包内 `relic_tables.RELIC_ROWS`**：平均值一律经 `_relic_average` 从那张表取，
  不要在任何地方再散抄数字。主程序 `nodes.RELIC_ROWS` 与它的差异由对拍测试报出来（改一边不跟另一边 = 红）。
- **不用 `random`**：所有概率/期望都必须来自解析公式或**精确枚举**；需要抽样时必须单独开函数并显式传入种子。
- **"最好"必须有全序**：状态向量之间是偏序，互不支配时没有"最好"。两种合法做法：
  ① 压成标量（`state_scalar`，词条总数；将来换真实伤害）→ `best_of_n` 给分数分布；
  ② 给状态一个**全序键**（`total_state_key`）→ `best_of_n_states` 给**向量分布**（口径 B，见 §11）。
- **有效词条集合由用户定义**（`check_effective`，任意 1~10 项），**不要**写死成某个常量；
  `DEFAULT_TRACKED` 只是早期接口的默认值。状态轴取 `effective` 或更宽的 `tracked`（如 `STATS_ORDER`）。
- 生命/防御/充能等不在**当前**集合里时，**只占词条池**（通过"入选概率"体现，不能直接丢掉）。
- 所有函数是**纯函数**：不读写全局状态、不改入参、不打印。

## 3. 数学约定

- 单件状态分布 `P₁[i]`：`{(词条次数向量): 概率}`，概率和必须为 1。
- 累积 `S[s] = P(单件分数 ≤ s)`。
- **N 件最好的万能通式**：

  ```
  P_N[s] = S[s]^N − (S[s] − P₁[s])^N
  ```

  只能对**标量**分数使用；多维偏序直接套会算出和不为 1 的结果（历史坑）。
- 精度写法：`S^N − (S−P)^N = S^N·(1 − (1 − P/S)^N)`，否则两个接近 1 的数相减会丢精度。
- 期望的线性可以用，但**不能把 `E[f(X)]` 换成 `f(E[X])`**（Jensen）：
  伤害链非线性（暴击封顶、乘区相乘），两者必须分开标注。
- **向量状态的 `P_N[v]` 只在「全序」下定义**（见 §11）：
  偏序（逐分量支配）只能给 `P(最好那个 ≥ v) = 1 − (1−q_v)^N`，那是"至少达到"口径，不是分布。

## 4. 测试约定（`tests/test_relic.py`）

必须覆盖的"对拍"：

1. **概率和 = 1**（单件分布、N 件分布）；
2. **枚举期望 = 解析期望**（逐属性，1e-9）——这是最强的正确性检查；
3. **N=2 与暴力枚举取 max 对拍**（1e-12）；
4. 概率表合计 100%、权重合计 1100、满级值；
5. 单调性：N 越大期望最好分数不减；q4 越大（34% vs 20%）期望更好；
6. 点数随 q4 变化：8 / 8.2 / 9；
7. **口径 B**（§11）：`best_of_n_states` 概率和为 1、N=1 恒等、按键投影 = `best_of_n`（1e-12）、
   N=2 与暴力枚举取键最大对拍（1e-12）、撞键必须报错。

跑法：`python -m pytest -q`（在仓库根），提交前必须全绿。

## 8. 伤害函数抽象与 DLL 加速（计划）

目标：圣遗物模拟/DP 要调用伤害链**几十万到几百万次**，Python 的图求值太慢。
做法：把"某工程的伤害链"抽象成一个**纯数值函数**，编译成 DLL，用 `ctypes` 调用。

### 8.1 分层

| 层 | 内容 |
|---|---|
| 抽象层 | `DamageFn = Callable[[Sequence[float]], float]` + 固定的**属性顺序** `stats_order` |
| 解释层 | 现有 `Graph.evaluate` 包一层（等价但慢，作为回退与对拍基准） |
| 生成层 | 把工程链**常量折叠**后生成 C 源码（只含算术表达式，不执行用户字符串） |
| 编译层 | MinGW `gcc -O3 -shared` → `damage_<指纹>.dll`，缓存到 **`build/dll/`**（`build/` 已在 `.gitignore` 里） |
| 调用层 | `ctypes` 载入；**批量接口**一次算 N 组，减少调用开销 |
| 回退 | 没有 gcc / 编译失败 / 指纹不符 → 自动走解释层，结果必须一致 |

### 8.2 约定

- 导出 ABI（草案）：
  - `int calc(const double* x)` → 返回伤害（`x` 按 `stats_order` 排列）
  - `void calc_batch(const double* x, int rows, double* out)` → 一次算 `rows` 组
- **生成 C 代码必须白名单**：只允许数字、四则运算、括号、已知变量名；
  用户填的算式先用现有求值器解析成数字/四则表达式再翻译，**绝不把原始字符串拼进 C**。
- 等价性：同一批随机属性，DLL 与解释层的相对误差 < 1e-9（pytest 用例守住）。
- 指纹：工程 JSON + 属性顺序 + gcc 版本 → 变了就重新编译。
- **DLL 不进 git**（编译产物、与平台/编译器绑定）：输出目录固定 `build/dll/`；
  生成的 C 源码（`build/dll/*.c`）同样不进 git，需要留档时另存。
- 不使用 `private/` 存放构建产物（`private/` 是个人存档，语义不同）。
- 只在 `relic` 的模拟/DP 用 DLL；**不改变工程本身的求值路径**（前端 `/api/evaluate` 仍走 Python）。

## 9. 伤害函数的输入向量（仅副词条口径）

只考虑**副词条**能给出的属性时，会进伤害公式的恰好是 **9 项**（顺序固定，下标即约定）：

| # | 宏 | 中文 | 单位 |
|---|---|---|---|
| 0 | `atk_pct` | 攻击% | 百分数 |
| 1 | `atk_flat` | 小攻击 | 绝对值 |
| 2 | `hp_pct` | 生命% | 百分数 |
| 3 | `hp_flat` | 小生命 | 绝对值 |
| 4 | `def_pct` | 防御% | 百分数 |
| 5 | `def_flat` | 小防御 | 绝对值 |
| 6 | `em` | 元素精通 | 绝对值 |
| 7 | `crit_rate` | 暴击率 | 百分数 |
| 8 | `crit_dmg` | 暴击伤害 | 百分数 |

约定：

- **`er`（元素充能效率）不在里面**：它不进伤害公式，只在词条池里占权重（拉低有用词条的入选概率）；
- 主词条另算（`dmg` 元素/物理伤害、`crit_rate/crit_dmg` 冠、`atk_pct/em` 沙杯），
  需要时在模拟层单独叠加，不要混进这 9 项；
- 数值一律 `float`，百分数按面板口径（`25.0` = 25%）；
- 这 9 项是**圣遗物模拟**的输入；完整工程求值（含 `month_dmg / res_shred / …` 等 20 个宏）
  仍由 `Graph.evaluate` 负责，两者不混用。

### 9.1 已实现的接口（解释层）

`genshin_dmg/GIRelic/relic_adapter.py`（需要工程的那一层）：

```python
STATS_ORDER                      # 9 个属性名，顺序即 ABI 下标（定义在 relic.py）

fn = damage_fn_from_project(project, role)   # project = 工程 dict 或文件路径
fn.calc([...9 个 float...]) -> float          # 单次
fn.calc_batch(rows) -> list[float]            # rows = 行优先扁平数组（长度 = 组数 × 9）
```

- 内部用 `Graph.extra_own`（**新增**，在 `graph.py`）把属性注入成该角色的**自身值**：
  面板里写过的宏相加、没写过的也登记；因此 `own::` 会包含圣遗物，`in::` 不会；
- 输入校验：长度必须 9、不得 NaN/inf、批量必须整除，错误一律 `ValueError`；
- 同一个 `Graph` 实例可反复求值（`evaluate` 会重置运行时状态），所以批量只重建 `extra_own`。

## 10. 与主体分离（接口化，重要）

圣遗物这一块**必须能脱离主程序单独存在**：主程序（画布 / `/api/evaluate` / 前端）不需要知道圣遗物，
圣遗物也不需要知道卡片类型、连线、前端。两边只通过下面这层**窄接口**接触。

```
relic_tables.py     参考表副本（RELIC_ROWS），零 import
relic_math.py       通用工具副本（mangle / 全角表 / 抗性系数 / 防御系数），零外依赖
relic.py            纯算术：树脂 / 主词条 / 副词条 / 单件状态分布 / 万能通式
relic_program.py    函数表示：run(程序, 属性) → 伤害（纯执行，不碰工程）
relic_adapter.py    ★唯一允许 import graph 的地方：GraphDamageFn / damage_fn_from_project /
                    compile_project（工程 → 上面两者）
```

副本与主体的一致性由 `tests/test_relic_independence.py` 对拍（值相等 + 静态 import 检查）；
该测试属于"主程序还在"时才成立的护栏，整目录搬走时删掉。

**状态：adapter 已落地**（`relic_adapter.py`）。`relic.py` / `relic_program.py` 里已无任何
`graph` 引用；`graph.py` 只在适配层的函数体内惰性 import，`import relic` 不会把图求值拖进来。

### 10.1 硬性规则

1. **`relic.py` / `relic_program.py` 不 import `graph.py`**。
   需要"从工程拿东西"时，只能接收**已经算好/编译好**的数据（属性向量、程序、常量表）。
   工程相关的两个入口（`GraphDamageFn` / `compile_project`）已经在 `relic_adapter.py`，
   纯算术层不再持有任何 Graph 引用。
2. **主体不得 import relic**：主程序不依赖圣遗物；将来要暴露功能，只加一个薄接口
   （如 `POST /api/relic/...`，且由 adapter 调用），不让画布/求值逻辑引用 relic。
3. **接口只认数字**：跨边界传递的只有 `list[float]`（9 个属性）、`dict` 程序结构、
   `float` 伤害值；不传 Graph 对象、不传卡片、不传前端字段。
4. **失败用异常表达**：不能编译的工程 → `NotCompilable`；输入非法 → `ValueError`。
   调用方据此回退解释层，不做静默兜底。
5. **可删性自检**：删掉 `relic*.py` 后主程序必须仍能完整运行（`pytest` 全绿）。

### 10.2 接口定义（草案）

## 11. 向量状态的 best-of-N（口径 B，用户指定）

"在 N 个胚子里，最好（最有效）的那个**恰好达到状态 v**"的概率。两种口径必须先分清：

| 口径 | 事件 | 是否分布 | 实现 |
|---|---|---|---|
| A 至少达到（支配） | `P(最好那个 ≽ v) = 1 − (1 − q_v)^N`，`q_v = Σ_{w ≽ v} P₁[w]` | 否（单调递减，求和 ≠ 1） | 未实现 |
| **B 恰好等于** | `P(最好那个 = v)` | **是**，`Σ_v P_N[v] = 1` | `best_of_n_states` |

### 11.1 定义与公式

`P_N[v]` 需要状态上的**全序**（偏序下"最好"不唯一）。给定全序键 `key`：

```
S[v] = Σ_{w ≤ v} P₁[w]                 # 按 key 累积
P_N[v] = S[v]^N − (S[v] − P₁[v])^N     # 与标量版同一个通式
       = S[v]^N·(1 − (1 − P₁[v]/S[v])^N)   # 精度写法，必须用这个
```

`N=1` 时退化为 `P₁[v]`；`N→∞` 时概率向最大键处分集中。

### 11.2 接口

```python
total_state_key(vector) -> tuple        # 默认键 (词条总数, 向量字典序)
best_of_n_states(states, n, key=total_state_key) -> {vector: prob}
```

`key` 契约（**硬要求**，违反就报错，不静默兜底）：

1. 可哈希、可比较（全序）；
2. 对状态**互不相同**——两个不同状态同键 → `ValueError("排序键不唯一…")`。
   同键时"最好那个等于 v"在数学上无定义；合并两个状态就只能得到**分数层**分布，
   那是 `best_of_n` 的职责，不能混进来。
3. `n <= 0` → `ValueError`。

**接真实伤害时**（步骤 4 完成后）：

```python
key = lambda v: (damage(v), tuple(v))   # 伤害为主序，伤害相等时用向量打破并列
```

只写 `key=damage` 会撞键（不同向量同伤害），必须拼上向量本身。

### 11.3 适用范围与成本

- **只适用于单槽**：单件状态数 = **466**（5 个追踪属性、词条总数 8~9），排序 O(M log M)，与 N 无关。
- **5 槽不能直接扩展**：`466^5 ≈ 2.1e13`，笛卡尔积不可行。多槽必须先投影到伤害标量做 DP，
  向量层只能给"边际分布"或"给定总分下的条件分布"（见 §6 步骤 5）。
- 主词条在这里是**条件**（`piece_states(main, ...)` 已按该主词条取池），不参与排序。

### 11.4 校验（`tests/test_relic.py::TestBestOfNStates`）

1. 概率和 = 1（N = 2/3/10/50），状态集不变；
2. `N=1` 就是 `P₁`；
3. 按 `key` 首分量投影 → 与 `best_of_n` 完全一致（1e-12）——证明两套实现同源；
4. `N=2` 与暴力枚举所有有序对取 `argmax` 对拍（1e-12），默认键与自定义"伤害型"键各一遍；
5. 任一键下期望随 N 单调不减；
6. 撞键、非法 N 必须抛 `ValueError`。

## 12. 带筛选的刷取模型（有效词条 + 接受条件，用户指定）

真实刷本不是"拿所有胚子",而是**先看初始词条、值得才强化**。这一层把"筛选策略"变成参数。

### 12.1 口径（已与用户确认）

见 §1「筛选」表。核心三点：

1. 有效词条集合 `E` 由**用户给定**，任意 1~10 项；
2. 判定时机：**4 起手 +0 / 3 起手 +4**（都要看到 4 条再判）；
3. 未通过的胚子**直接丢弃** → 产出是**条件分布** `P(状态 | 通过)`，不是混合分布。

### 12.2 恒等式（重要，别"优化"掉）

"先抽 3 条、+4 再补第 4 条"与"直接顺序抽 4 条"是同一件事（第 4 次抽样），
所以**两种起手的判定时刻集合分布完全相同**，差别只在后续强化次数：

| 起手 | 概率 | 判定后剩余强化 | 满级点数 |
|---|---|---|---|
| 4 条 | `q4`（副本 0.2） | 5 次 | 9 |
| 3 条 | `1-q4` | 4 次 | 8 |

由 `test_four_and_three_starts_share_the_same_set_distribution` 守住（14 位小数）。

### 12.3 接口

```python
POOL_KEYS                                   # 10 项副词条池（元素伤害/物理/治疗没有副词条）

check_effective(effective) -> tuple          # 校验 + 去重，任意 1~10 项；非法/空 → ValueError
start_line_sets(main, q4) -> {(frozenset(4 条), "four"|"three"): prob}
effective_lines(lines, effective) -> int     # 这 4 条里有几条有效
pass_probability(main, effective, k, q4) -> float
filtered_piece_states(main, effective, k, q4, tracked=None) -> {vec: prob}   # 条件分布，和为 1
filtered_summary(...)                        # {"pass_rate", "states", "expected_rolls", …}
resin_per_accepted(slot, main, effective, k, off_piece, q4) -> float
```

- `tracked` 默认 = `effective`；传更宽的（如 `STATS_ORDER`）可保留其它属性的次数，供伤害打分（步骤 4）。
- 错误语义：`filtered_piece_states` 在"没有胚子能通过"时抛 `ValueError`；
  `pass_probability` 返回 `0.0`；`resin_per_accepted` 返回 `inf`。
- `resin_per_accepted = resin_cost(slot, main) / pass_rate`；强化材料不建模（用户口径）。

### 12.4 与既有模型的关系

- 不筛选时（`k <= 1` 且 `E = 全池`）必须等于 `piece_states(tracked=E)`（1e-14，测试守住）；
- 筛选后的条件分布可直接喂给 `best_of_n` / `best_of_n_states`；
- 5 槽联合与预算约束仍未做（§6 步骤 5）。

### 12.5 参考数字（沙·攻击% 主词条，目标套，`E = (crit_rate, crit_dmg, atk_flat)`）

| k（至少几个有效） | 通过率 | 期望树脂/件 |
|---|---|---|
| 1 | 85.2% | 826 |
| 2 | 33.4% | 2 107 |
| 3 | 3.0% | 23 728 |
